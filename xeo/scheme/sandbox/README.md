# Песочница xeo

Место для набросков версий библиотеки: как xeo может работать с частью данных, без полного снимка базы. Здесь думают
над устройством библиотеки и над тем, как ею пользуется приложение, — на маленькой схеме, настоящем сервере и настоящем
клиенте, рядом друг с другом. Песочница принадлежит пакету `xeo-scheme`, но стоит на всех трёх библиотеках: `scheme`,
`toolkit`, `react`. Пример у всех версий один, и экран один: каркас и блоки экрана живут в `app/kit` на uikit и formkit,
версия собирает из них свой экран на своей библиотеке.

## Устройство

```
sandbox/
  server/          хост NestJS: монтирует серверный модуль каждой версии под префиксом её ключа (/v-current/...)
  app/             приложение Vite: стартовая со списком версий, экран версии — по первому сегменту адреса (/v-current/...)
    kit/           готовые блоки экрана для всех версий (раздел «Экран»)
    styles/        все стили приложения: сброс, тема uikit, токены песочницы, блоки kit
  versions/        наброски версий
    v-current/     текущая библиотека как она есть — точка отсчёта
      lib/         поверхность библиотеки версии: что версия даёт приложению
      core/        «ядро» приложения на этой библиотеке: схема, домены, параметры операций
      server/      серверный модуль версии: журнал, снимок или его замена, поток событий, посев
      client/      клиент версии: локальные данные и хуки, формы действий, приложение App, экран из блоков kit
      README.md    что версия показывает, что меряет, что в ней замечено
      xeo-visual.config.ts  каркас карты схемы версии; карта — core/scheme-map.html и .svg
  scripts/         dev.js — сервер и приложение одной командой; visual.js — карты схем версий
```

Правило версии: `core`, `server` и `client` импортируют библиотеку только из своего `lib/`. У `v-current` это
реэкспорт опубликованных пакетов; следующие версии подменяют или дополняют экспорты своим наброском, и по `lib/` видно,
чего версия требует от библиотеки. Версии не импортируют друг друга: новая версия — копия предыдущей со своими
изменениями, чтобы каждую можно было читать и запускать отдельно. Общее у версий — только `app/kit`.

Реестры версий — `app/versions.ts` (клиенты, с описанием для стартовой) и `server/versions.ts` (серверные модули). Новая
версия — папка в `versions/` и строка в обоих реестрах.

## Экран

Экран версии — две половины. Слева дашборд: шапка с именем версии, под ней Domains Operations и Networks. Справа — App:
клиентское приложение версии, как его строил бы настоящий клиент на этой библиотеке. Граница между `app/kit` и версией
проходит по библиотеке: всё, что читает данные приложения и вызывает операции, зависит от библиотеки версии и
собирается версией; kit даёт каркас, view и блоки, которые библиотеки не знают.

| Часть              | Чья                 | Что                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------ | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Каркас             | kit                 | `SandboxScreen` — дашборд (шапка с ключом версии и кнопкой «Сбросить базу» — сброс даёт версия пропом `onReset`, после него страница перезагружается; плашка `ResyncBanner`; колонки `domains`, `network`) и половина `app`, окна и тосты kit; `SandboxScreen.Message` — экран одного состояния (подключение)                                                                                                                                                      |
| Domains Operations | kit по карте версии | `DomainsPanel` по карте `DomainGroup[]`: домены группами, в группе — действия с именем метода и хуком формы. Кнопка действия открывает окно kit; форму пишет версия сама (`client/forms`: хук `use<Name>Form` на действие, formkit на полях kit) и в отправке вызывает операцию через `run` — успех закрывает окно с тостом, отказ — тост                                                                                                                          |
| Networks           | kit                 | `NetworkPanel` — все обмены с сервером вместо вкладки Network браузера: запросы (метод, адрес, заголовки, параметры, статус, ответ, вес, время) и сообщения потока. Версия ходит на сервер через `network.fetch` и `network.stream`; подпись строки по своему протоколу даёт пропом `summary`                                                                                                                                                                      |
| App                | версия из view kit  | приложение версии на `react-router` (`client/App/` у `v-current`): роутер с `basename` — префиксом версии, страницы — файлами папки. Корень (`/v-current`) — главная, раздел — полный список (`/v-current/workers`), запись — `/v-current/workers/12`. View kit — `AppFrame` (строка разделов), `AppPage` с частями `Section` и `Empty`, `SectionTiles`, `RecordFields` (поля-ссылки ведут в связанные записи), `RecordsTable` (все записи, строка ведёт в запись) |

Окна kit — реестр uikit `createPopupRegistry` (`kit/popups.ts`), формы — `@companix/formkit` с полями над контролами
uikit (`kit/formkit/`: примитивы и раскладки, как пакет `formkit` CRM). Итог операции — тост uikit (`kit/toaster.tsx`):
успех закрывает окно, отказ оставляет его открытым. JSON в Networks — деревом `react-json-view-lite` со своими классами
подсветки: узлы сворачиваются, глубже второго уровня свёрнуто сразу. Стили — по владельцам в `app/styles/components`,
только SCSS с токенами темы (`app/styles/tokens.scss`, светлая тема), без Tailwind — как в CRM-клиенте.

## Запуск

Один раз — зависимости в корне `@libs` (`npm install`): пакет `@companix/xeo-sandbox` объявлен в `workspaces`. Затем:

```
npm run dev -w=@companix/xeo-sandbox        # сервер :4500 и приложение :4501 вместе
npm run server -w=@companix/xeo-sandbox     # только сервер (tsx watch)
npm run app -w=@companix/xeo-sandbox        # только приложение (vite)
npm run visual -w=@companix/xeo-sandbox     # карты схем всех версий; одна — `-- <version>`
npm run typecheck -w=@companix/xeo-sandbox  # типы всей песочницы вместе с исходниками библиотек
```

Приложение — http://localhost:4501, версия — http://localhost:4501/v-current. Запросы `/api/<version>/...`
приложение проксирует на сервер, так что адрес сервера клиент не знает. Второе окно браузера — второй клиент: по нему
видно, как реплики узнают о чужих изменениях. Сервер засевается заново при каждом перезапуске и по кнопке «Сбросить
базу» в шапке — открытые страницы видят новую эпоху и просят перезагрузку.

## Как устроено окружение

- **Библиотеки из исходников.** Vite (`app/vite.config.ts`, алиасы) и TypeScript (`tsconfig.json`, `paths`) ведут
  `@companix/xeo-scheme`, `xeo-toolkit` и `xeo-react` в `lib/` пакетов, а не в `dist`: правка библиотеки видна без
  сборки, и хранилище метаданных моделей (модульный синглтон `xeo-scheme`) одно у всех пакетов. `globalThis.__DEV__`
  в сборке приложения — `false`: отладочные логи xeo выключены.
- **uikit и formkit тоже из исходников** (`packages/uikit/src`, `packages/formkit/src`), как в песочнице uikit: тема
  `themes/classic` копит токены в карте модуля `src/theme.scss`, и его компоненты должны собираться из той же `src`.
  Алиас Vite — только на точное имя пакета; стили подключаются путями `@companix/uikit/...` в `app/styles/index.scss`.
- **Сервер без базы.** База сервера — тот же in-memory драйвер xeo, что у клиента; при старте сервер засевается
  операциями доменов (детерминированно, та же база на каждый запуск). Песочница думает о протоколе между приложением
  и библиотекой, не о хранилище; когда вопрос дойдёт до запросов к Mongo, версия подключит `xeo-server` в своём
  серверном модуле.
- **Карты схем — `@companix/xeo-visual`** через его API `buildSchemeMap` под `tsx` (`scripts/visual-build.ts`): схема
  версии грузится из исходников, как на сервере; CLI `xeo-visual` грузит TypeScript-конфиг через `ts-node`, которого в
  libs нет. Конфиг версии — в формате инструмента (`xeo-visual.config.ts`, пути — от его папки); каждая версия
  собирается в своём процессе — декораторы двух схем в одном процессе задвоили бы хранилище метаданных.
- **Сервер на `tsx`.** esbuild не пишет метаданные декораторов, поэтому зависимости в конструкторах NestJS указываются
  явно — `@Inject(Service)`.
- `tsconfig.json` подключает глобальные типы `multer`: исходники `utils-browser`, которые берёт uikit, тянут `xeo-types`
  с `Express.Multer`.
- Стиль кода — `code-style` автора; устройство клиента — по образцу `ARCH.md` CRM-клиента (view и controller, окна
  через реестр, формы formkit, стили по владельцам); документы и комментарии — по-русски.
