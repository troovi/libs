# v-0.1.32 — опубликованная библиотека

Точка отсчёта: библиотеки xeo как они опубликованы и как ими пользуется CRM — `xeo-scheme` 0.1.32, `xeo-toolkit` 0.1.1,
`xeo-react` 0.1.3, закреплённые в `package.json` версии ссылками на tarball из npm. Исходники xeo в libs уходят вперёд,
а версия остаётся на этих пакетах. Приложение при входе получает весь снимок базы, дальше живёт событиями журнала:
сервер выполняет операцию домена, рассылает событие, клиент повторяет тот же метод домена над своей базой; экран читает
локальную базу синхронно хуками. Версия нужна, чтобы видеть и мерить исходную точку, и чтобы следующие версии было с чем
сравнивать — тем же экраном, на той же схеме; с неё же начинается форк новой версии (README песочницы).

## Что внутри

**Схема** (`core/scheme.ts`) — восемь коллекций, в которых есть каждый вид связи xeo: `worker` (дискриминированная
модель, embedded-контакты, регионы — `ReferenceSet` значений справочника, гражданство — `ReferenceTo` с `set-null`),
`client` → менеджер, `project` → клиент и набор кадровиков (`ReferenceSet`), `shift` → проект с embedded-итогами и
`HasMany` участников с каскадом, `participant` (`BelongsTo` смены, `ReferenceTo` сотрудника), справочники как в CRM —
`dictionary` (ключ из перечня `AppKeys.Dictionary`: `regions`, `citizenships`) с `HasMany` значений `option` каскадом,
`counter` — счётчики номеров.

**Домены** (`core/domains/`) — пять классов на `Collections<AppScheme>`, как в CRM: `dictionary` (посев словарей
системой, добавление, переименование и удаление значения — названия уникальны в словаре без учёта регистра; удаление, в
отличие от CRM, настоящее: схема снимает значение с сотрудников), `workers` (создание офисного и ревизора с регионами и
гражданством из своих справочников, переименование, увольнение), `clients` (создание, удаление — клиента с проектами
остановит схема), `projects` (создание, завершение), `shifts` (создание, запуск набора, состав, явка, завершение с
начислением, отмена). Параметры — zod через `schemaOf`; реестр схем для проверки тела запроса (`params.ts`) читает
только сервер.

**Сервер** (`server/`) — `createServerShell` над in-memory базой: очередь вызовов, контекст с лентой идентификаторов,
ревизии. Маршруты под `/v-0.1.32`: `POST domains/<domain>/<method>` (актор — заголовок `x-worker-id`, без него —
система), `GET snapshot`, `GET events` — поток событий SSE (вместо сокета CRM: та же односторонняя рассылка, без
зависимостей), `GET stats` — сводка для сравнения, `POST reset` — сброс базы: пустая база с новой эпохой и посев
заново; подключённым репликам — `resync`, посев им не рассылается. Посев при старте — около трёх тысяч операций
доменов.

**Клиент** (`client/`) — `createClientShell` над своим in-memory источником, `createDataSourceHooks`, `DomainsAPI` поверх
`fetch`. Порядок старта — как в CRM: поток событий, затем снимок, затем применение накопленного. Поток, снимок и вызовы
идут через `network` kit. Экран — каркас и блоки `app/kit` (README песочницы, «Экран»), слева дашборд, справа приложение:

- Domains Operations — панель kit по карте `forms/index.ts`: на каждое действие домена — свой хук формы
  `forms/use-<name>-form.ts` (formkit на полях kit, выбор записей — короткие примитивы
  `forms/shortcuts/entities.shortcuts.ts` на `useAll`), отправка вызывает `DomainsAPI` через `run` окна: успех — тост с
  результатом и закрытие окна, отказ домена и ошибка целостности — тост с текстом сервера;
- Networks — запросы и сообщения потока; строка события журнала подписана ревизией и методом домена.
- App (`App/`) — приложение версии на `react-router` под префиксом `/v-0.1.32`: главная с разделами, полные списки
  (`WorkersPage`, `ClientsPage`, `ProjectsPage`, `ShiftsPage`, `DictionariesPage` — `useAll`, свежие сверху) и записи
  (`WorkerPage` — со значениями справочников через `useEntities`, `ClientPage`, `ProjectPage`, `ShiftPage`,
  `DictionaryPage` — `useEntity` и связанные через `useFindBy`); пути — `App/paths.ts`.

**Карта схемы** — `core/scheme-map.html` (и `.svg`), собирается `npm run visual -w=@companix/xeo-sandbox` по
`xeo-visual.config.ts`: модели, поля с JSDoc и типами, embedded-блоки и связи.

## Что меряется

Networks показывает вес и время каждого запроса, в том числе снимка, и вес каждого сообщения потока; App — число
записей по коллекциям. Сводка сервера — `GET /v-0.1.32/stats`: записи по коллекциям, вес снимка в байтах JSON, число
строк связей, посев. Размеры посева — константы `SIZES` в `server/seed.ts`: их меняют, чтобы увидеть, как растёт
снимок. Вызовы экрана идут от имени системы: сервер принимает актора заголовком `x-worker-id`, но домены версии его не
проверяют.

## Замечено при сборке

Факты о текущей библиотеке, которые всплыли, пока версия собиралась; не решения.

- `getTables()` базового драйвера отдаёт отладочный вид (`{ m1: { id: [ids] } }`), а снимок `createServerShell` ждёт
  строки `{ m1, m2 }`, как у Mongo-драйвера: сервер на in-memory базе без адаптера не собирает снимок
  (`tableRowsOf` в `server/journal.service.ts`; ключи объекта — строки, числовые идентификаторы восстанавливаются
  по типу идентификатора модели).
- `schemaOf` не входит в индекс `xeo-toolkit` — отдельный вход `dist/schemaOf`, чтобы zod не попадал в сборку клиента.
- `xeo-scheme` и `xeo-react` оба экспортируют имя `MutationEvent`; `export *` из обоих пакетов в одном модуле не
  компилируется — `lib/react.ts` реэкспортирует из `xeo-react` только `createDataSourceHooks`.
- Сборки пакетов в npm разные: `xeo-scheme` — CommonJS и ESM, `xeo-toolkit` 0.1.1 — только CommonJS, `xeo-react`
  0.1.3 — только ESM (`module` без `main`). Отсюда два обхода в `lib/`: из `xeo-toolkit` значения реэкспортируются
  перечнем — `export *` из CommonJS Vite при пред-сборке не разворачивает; хуки — отдельный вход `lib/react.ts`,
  потому что сервер на `tsx` загружает `lib/index.ts` как CommonJS и `xeo-react` загрузить не может.
- `EventSync` не даёт подписки «событие применено» — только `whenApplied(revision)` на отдельное событие.
- Расхождение реплики с сервером (смена эпохи, разрыв ревизий, ошибка повтора, обрыв потока) — только
  пересинхронизация целиком; в CRM это перезагрузка страницы, здесь — плашка с кнопкой.
- Операция, упавшая после `ctx.ids.number(...)`, оставляет счётчик сервера сдвинутым без события: реплики о сдвиге
  не знают, а новая реплика получает его со снимком — состояния расходятся до следующего выданного номера
  (`ReplayTape.number` подтягивает `seq` до значения из ленты). Запись счётчика частичной записью не считается.
  Всплыло на `projects.create` с несуществующим кадровиком: отказала схема, но номер уже был взят.
  Отсюда правило CRM «идентификаторы — после всех проверок»; в песочнице проверка кадровиков теперь до номера.
